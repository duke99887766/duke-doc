# 产品需求文档输出

## 工作目标

将已确认需求组装成深度适当、研发可执行的规范性文档，只更新本轮变化和直接配套资产，不重新发明业务规则或启动完整需求编排。

## 输入要求

优先使用增量需求包：

- 需求主题、阶段、本期范围和明确排除项；
- 本轮新增、修改或废弃的 `R-xxx`；
- 需要新增或重新验证的 `AC-xxx`；
- 保持不变的规则范围；
- 目标文档、直接配套索引和原型入口；
- 已授权的写入范围；
- L1、L2 或 L3 交付等级。

缺少会改变核心方案的信息时返回阻塞项，不开展完整访谈。非阻塞信息缺失时可以输出标记清晰的草稿。

## 参考资料按需读取

正式输出前读取 [通用文档契约](references/spec-contracts.md)，然后只读取当前交付等级对应的结构：

- L1 轻量 Spec 或一页看板：[L1 输出结构](references/spec-l1.md)；
- L2 标准需求或 L3 完整 PRD：[L2/L3 输出结构](references/spec-l2-l3.md)；
- 需要 Frontmatter、README 索引或原型入口同步时，再读取 [工作区同步约定](references/workspace-sync.md)；
- 多阶段、已上线续期或版本边界变化时，再读取 `../duke-doc/references/phase-version.md`。

不要同时读取不相关的 L1 与 L2/L3 模板。已在本轮读取且文件未变化的契约不重复读取。

## 工作流程

1. 采用传入等级；直接调用且未指定时选择最轻的可用等级。
2. 确定唯一规范性文档；README 索引、Frontmatter 和原型入口属于同一文档阶段，不因此启动 `duke-doc`。
3. 恢复目标章节和本轮变化，只在范围变化、资产被外部修改或追溯不清时重读全文。
4. 只将已确认规则写成确定结论；建议、原型方案、实现默认、数据发现和待确认项保持原性质。
5. 按当前等级契约更新变化章节，保留 `R-xxx`、`AC-xxx` 及其对应关系；不复制未变化的完整规则包。
6. 有原型时维护正文首屏研发快速入口；无原型时不输出空入口。
7. 只更新有证据直接承载本轮规则的文档、索引和链接；覆盖范围不清时标记“需核对”。
8. 完成一轮批量写入后，对每个变更文档执行一次 `check_requirement_docs.py`，修复阻塞错误，再按工作区规范执行一次 `verify-workspace.ps1 -ChangedOnly`。
9. 阶段交付或批量治理时才运行全量工作区校验；不在每个标题、表格或链接修改后重复校验。

## 写入和表达要求

- 只有用户明确授权时写入对应文件；未授权资产列为待同步。
- 默认使用中文，简洁、结论化、可执行和可验证。
- 字段、状态、规则、角色或场景需要比较时使用表格；简单内容不强制制表。
- 使用精确状态名、字段名、按钮名、提示语和记录文案。
- 不适用章节直接省略；不为形式完整虚构指标、数据、异常、权限或系统影响。
- 文件名使用“业务主题-文档类型.md”，避免“最终版”“最新版”。
- 更新活跃文档时同步维护 Frontmatter 和 `更新时间`，Frontmatter 只保存事实字段。
- `负责人`使用实际维护人；无法确认时留空并标记待补充，不使用角色占位。
- 有原型时，只有原型覆盖当前有效规则并通过校验才标记“已同步”。
- 更新记录统一放在正文最后。只有用户明确要求且工作区允许版本化时才维护文档版本；不得创建产品文档快照或版本副本。

## 校验命令

每个新建或更新的 Markdown 文档在一轮编辑完成后执行一次：

```powershell
python scripts/check_requirement_docs.py <文档路径>
```

按需增加 `--require-frontmatter`、`--index <README路径>`、`--expect-update-date YYYY-MM-DD` 和 `--repo-root <仓库目录>`。阻塞错误必须修复；只汇总变更文件的警告和既有未受影响警告，不因后者重复运行校验。

## 交付结果

只说明：

- 已更新资产及对应规则编号；
- 原型入口和同步状态；
- 已校验但无需修改的直接资产；
- 未授权、缺文件或待确认而未同步的资产；
- 文档口径冲突及最终校验结果。

不要在回复中复制已经写入文件的完整正文。

## 输出边界

- 不从模糊想法开展完整需求访谈。
- 不制作 HTML 原型；原型交给 `duke-build-requirement-prototype`。
- 不独立生成详细验收场景；需要时交给 `duke-write-acceptance`。
- 不默认进行全面文档评审；用户明确要求、L3、高风险或结构性冲突时交给 `duke-review-spec`。
- 不读取代码或截图判断实际实现。
