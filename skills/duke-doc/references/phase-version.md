# 阶段与版本协议

## 1. 分离三个概念

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 业务阶段 | 需求范围和交付边界 | 第一阶段、第二阶段2A、第二阶段2B |
| 文档版本 | 同一文档内容的修订序列 | V1.0、V1.1、V2.0 |
| 发布版本 | 产品或系统实际发布批次 | 2026.08、Release 2109 |

三者不得相互推断。“第二阶段”不等于文档 `V2.0`，文档 `V1.2` 也不代表产品发布两次。

## 2. 阶段树

每个阶段至少记录：

- 阶段编号或名称；
- 本期目标和范围；
- 明确排除项；
- 继承的前期规则；
- 本阶段独有规则；
- 被后续阶段替代的规则；
- 对应文档和原型资产；
- 当前推进状态。

阶段拆分后，优先为范围独立、可单独研发验收的阶段建立独立文档。后续阶段通过关联关系引用前期规则，不复制后再各自维护。

## 3. 文档版本

- 初次正式沉淀使用 `V1.0`。
- 不改变核心范围和主流程的补充使用 `V1.1`、`V1.2`。
- 核心范围、主流程、对象关系或关键规则发生重大变化时升级 `V2.0`。
- 仅修正错字、格式或链接时可以不升级版本，但必须按文档库规范更新时间。
- 已上线版本的新一期延伸需求应建立新阶段或新文档，只保留新改动并关联既有生效版本，不复制全部旧需求。

## 4. 防覆盖规则

- 更新前确认目标资产对应的业务阶段和文档版本。
- 后续阶段不得把前期生效规则改写成“本期新增”。
- 前期规则需要修改时，明确是回补前期、跨阶段公共规则还是后期替代规则。
- 同主题多文档存在时，依据阶段范围和规则编号决定传播对象；覆盖关系不清时标记“需核对”。
- 归档旧版本前确认当前有效版本、索引和关联链接已经切换。
