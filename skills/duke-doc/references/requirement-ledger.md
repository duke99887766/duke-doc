# 需求状态账本协议

## 1. 目的

在长周期、多轮、多阶段需求中保存唯一可信口径。账本用于内部协作和交接，不默认原样写入正式PRD。

## 2. 条目模型

每个条目至少包含：

| 字段 | 规则 |
| --- | --- |
| 条目编号 | 业务规则使用 `R-xxx`，问题使用 `Q-xxx`，数据发现使用 `D-xxx`；创建后不复用 |
| 内容 | 使用可独立理解的完整陈述，不只记录“可以”“沿用现状” |
| 内容性质 | 业务规则、待确认问题、原型方案、实现默认、数据发现、建议 |
| 确认状态 | 已确认、待确认、暂缓、已废弃 |
| 所属阶段 | 明确到本期或子阶段；跨阶段时列出全部适用阶段 |
| 适用范围 | 页面、对象、业务线、订单类型或全部 |
| 来源 | 用户确认、现有文档、原型、数据文件、实现证据或系统现状 |
| 变更关系 | 新增、修改、替代、被替代、废弃；引用关联编号 |
| 影响资产 | 原型、PRD、专项规范、验收标准、索引等 |

## 3. 内容性质约束

- 只有用户明确确认或权威现有文档能够证明的内容，才能标为“已确认业务规则”。
- 原型中的布局、文案和交互默认标为“原型方案”，除非用户明确确认其业务含义。
- 为使系统可运行而补充的非业务选择标为“实现默认”，不得掩盖阻塞问题。
- 数据样本产生的结论标为“数据发现”，附来源和样本限制，不直接升级为全量业务事实。
- `D-xxx` 只表示可追溯的数据证据；用户确认处理方式后另行形成 `R-xxx`，不要直接改号覆盖。
- Skill提出的处理方式标为“建议”，用户确认后再转换为业务规则。

## 4. 更新规则

1. 先恢复已有条目，再处理用户本轮输入。
2. 将用户简短回答改写成包含上下文的完整结论。
3. 内容修改但业务主题不变时保留编号并记录旧内容。
4. 规则被新规则替代时，将旧规则标记“已废弃”，并互相引用。
5. 问题得到回答后，将问题标记关闭，并将结论写入对应规则；不要删除问题历史。
6. 不确定用户是在修改规则还是补充示例时，保持待确认，不静默覆盖。

## 5. 输出模式

### 增量模式

日常多轮沟通默认输出：

- 本轮新增；
- 本轮修改或废弃；
- 本轮已关闭问题；
- 当前剩余待确认问题；
- 新增的影响资产。

### 快照模式

用户要求“确认一下当前需求”“整理待确认问题”或阶段收口时，输出完整的：

- 阶段树和范围；
- 已确认规则；
- 待确认问题；
- 暂缓与已废弃项；
- 资产同步状态。

## 6. 长任务恢复包

长任务、连续原型调整或可能发生上下文压缩时，在当前 Codex 任务中维护紧凑恢复包，不单独创建产品文档、快照文件或版本副本。

仅在阶段切换、`R/Q/AC` 状态变化、目标资产变化、完成写入/校验或即将发生上下文压缩时刷新。普通问答、重复检查和无状态变化的读取不刷新恢复包。

恢复包最多 20 行，使用以下顺序：

1. 当前需求主题、阶段和本期范围；
2. 唯一规范性文档及当前有效原型；
3. 本轮新增、修改或废弃的 `R/Q/AC`；
4. 当前目标页面、DOM 区域或交互场景；
5. 本轮仍有效的已读规则和参考；
6. 最近一次专项、浏览器和工作区校验结果；
7. 下一步动作及升级为 C1/C2 的条件。

恢复时先核对用户新输入是否改变范围，再读取恢复包指向的目标片段。文件时间、内容或用户说明表明资产已变化时，放弃缓存结论并重新读取相关完整资产。已在本轮读取且未变化的资料不得重复读取。
