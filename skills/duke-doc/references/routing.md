# 路由与交接协议

## 路由判断

| 用户请求 | 执行方式 |
| --- | --- |
| 模糊想法、需要一起梳理 | `duke-interview-requirement` |
| 已确认规则，需要写文档 | `duke-write-spec` |
| 需要验收标准或测试场景 | `duke-write-acceptance` |
| 已有 Spec/PRD，需要评审 | `duke-review-spec` |
| 同时提供需求与实现证据 | `duke-check-implementation` |
| 明确调用 `$duke-doc` 或包含两个以上阶段 | 进入编排流程 |

## 复杂度判断

| 维度 | L1 轻量 Spec | L2 标准需求 | L3 完整 PRD |
| --- | --- | --- | --- |
| 修改范围 | 单页面、单配置项或已有规则小改 | 多页面、模块或对象联动 | 多个核心系统或业务域 |
| 方案状态 | 已基本确定 | 主方案明确，需梳理分支 | 存在重大取舍或尚未收敛 |
| 系统能力 | 使用已有机制 | 调整已有能力或增加可控联动 | 新增关键链路、接口或基础能力 |
| 数据影响 | 无迁移或普通字段变更 | 有限存量兼容 | 大规模、复杂或不可逆迁移 |
| 风险 | 可恢复且影响有限 | 一致性、权限或依赖风险可控 | 资金、安全、合规或重大一致性风险 |

优先判断失败后果、可逆性和是否引入新机制，不按命中项机械计分。

## 统一需求包

专业 Skill 之间使用以下字段交接，只传递当前阶段需要的内容：

| 类型 | 字段 |
| --- | --- |
| 基础信息 | 需求主题、背景、当前问题、目标 |
| 用户信息 | 目标用户、操作角色、受影响角色 |
| 范围 | 本期范围、非本期范围 |
| 业务规则 | 规则编号、触发条件、系统处理、结果、反馈 |
| 流程 | 主流程、替代流程、失败流程、人工路径 |
| 状态 | 当前状态、允许状态、禁止状态、目标状态 |
| 权限 | 操作权限、数据权限、角色差异 |
| 异常 | 失败、部分成功、超时、重试、补偿 |
| 系统影响 | 页面、服务、接口、数据、上下游 |
| 风险 | 一致性、迁移、安全、资金、合规 |
| 管理信息 | 待确认项、阻塞项、明确排除项 |

## 编号和变更规则

- 业务规则使用 `R-001`、`R-002` 连续编号。
- 验收场景使用 `AC-001`、`AC-002`，并引用对应规则编号。
- 实现验收继续引用业务规则编号，不重新编号。
- 后续 Skill 不得静默改变已确认事实；发现冲突时记录差异并返回确认。
- 需求发生变更时，保留原编号并记录新旧规则；只有规则被删除时才标记废弃，不复用编号。

## 组合流程

### 端到端需求交付

`访谈（按需） → 验收标准 → 文档输出 → 文档评审`

### 已有文档修订

`文档评审 → 用户确认业务变更 → 文档输出`

### 实现验收

`需求口径检查（按需） → 实现验收`

### L1 快速流程

已有信息足够时跳过完整访谈，只建立简要需求包，再执行验收标准、轻量 Spec 和轻量读者检查。
