# 需求原型构建

## 工作目标

把已确认业务规则转化为可交互、可验证、可在浏览器预览的HTML需求原型。原型用于需求对齐，不替代正式PRD或生产代码。

## 输入要求

优先接收：

- 需求主题、阶段和适用场景；
- 带 `R-xxx` 编号的已确认业务规则；
- 单独标记的原型方案、实现默认和待确认项；
- 需要创建或更新的HTML文件路径；
- 参考截图、现有页面或既有原型；
- 本轮变更及影响组件。

缺少核心业务规则时，不从截图或旧原型反推并确定规则。可以制作演示稿，但必须把补充内容标为原型假设。

## 工作流程

正式操作前读取 [原型输出与验收契约](references/prototype-contract.md)。构建后台管理、运营或配置页面时，再读取 [NG-ZORRO 后台原型指南](references/ng-zorro-admin-patterns.md)。

### 1. 确定操作方式

- 用户提供既有HTML或原型工程时，在原文件基础上增量修改，保留无关功能、既有组件体系和用户已有改动。
- 用户要求新建后台管理、运营或配置页面，且没有既有设计体系约束时，优先复制 [NG-ZORRO 后台单文件模板](assets/admin-ng-zorro-prototype.html) 后修改。
- 用户要求新建其他浏览器预览文件时，复制 [基础HTML模板](assets/base-prototype.html) 后修改。
- 用户明确提供 Angular 原型工程时，在工程内实际使用与 Angular 18 匹配的 `ng-zorro-antd@18.2.x`；不要只为套用组件库而新建 Angular 工程。
- 用户只要求建议或评审时执行只读检查，不修改文件。

### 2. 分离规则性质

- 已确认业务规则：实现并使用 `data-requirement-id="R-xxx"` 标记关键组件。
- 原型方案：可以演示，但不得写成确定业务结论。
- 实现默认：只用于补足非业务交互，并在交付说明中列出。
- 待确认项：不擅自选择会导致不同业务结果的方案。

### 3. 构建页面和场景

- 按“既有产品一致性 → 后台页面 NG-ZORRO 18.2.x → 通用轻量原型”的顺序选择组件体系；用户明确指定其他体系时遵循用户指定。
- 后台页面优先复用 NG-ZORRO 的布局、表单、表格、筛选、分页、抽屉、弹窗、状态与反馈组件语义，不用自定义控件重复实现已有模式。
- 单文件HTML原型使用原生HTML、内联CSS和原生JavaScript复刻 NG-ZORRO 的组件结构、状态和视觉规范，不引入 Angular 运行时或不必要的外部依赖。
- 移动端、营销页和非后台页面不默认套用 NG-ZORRO；延续参考页面或选择适合场景的轻量结构。
- 使用场景状态驱动三方与非三方、空值与有值、首次与后续、成功与失败等差异，不复制多套易漂移页面。
- 对表单、筛选、时间线和弹层提供完成需求验证所需的最小交互。
- 兼顾信息密度、层级、键盘可用性、标签关联和空状态，不以纯视觉图片替代交互。

### 4. 维护追溯关系

- 在承载业务规则的关键DOM节点上添加 `data-requirement-id`；一个规则可对应多个节点。
- 变更既有组件时记录其对应规则编号。
- 不强制为纯视觉间距、颜色和无业务含义的装饰建立规则编号。
- 输出本轮“规则编号—组件—场景”摘要，不默认创建额外说明文档。

### 5. 校验

每次创建或修改HTML后执行：

```powershell
python scripts/check_html_prototype.py <html文件>
```

必须处理脚本报告的错误；警告根据原型目标判断并说明。具备可用浏览器控制能力时，再检查关键场景、交互和视觉溢出；本地浏览器不可访问时，使用静态校验并明确视觉验收尚未执行。

### 6. 交付

说明：

- HTML文件路径；
- 页面类型、采用的组件体系及偏离默认优先级的原因；
- 已实现的规则和场景；
- 原型假设或实现默认；
- 静态检查和浏览器检查结果；
- 尚待同步到PRD、验收标准或专项规范的规则。

## 修改边界

- 只有用户明确要求创建或更新原型文件时才写入。
- 不把原型中的交互细节自动升级为业务规则。
- 不修改正式PRD、专项规范或README索引；将影响项交给 `duke-doc` 或 `duke-write-spec`。
- 不将需求原型扩展为生产框架、接口实现或后端服务。
- 不覆盖与本次需求无关的现有修改。
