# 路由与交接协议

## 路由判断

| 用户请求 | 执行方式 |
| --- | --- |
| 模糊想法、需要一起梳理 | `duke-interview-requirement` |
| 提供历史明细、Excel或CSV并要求验证需求规则 | `duke-analyze-requirement-data` |
| 已确认规则，需要浏览器可预览的页面或交互验证 | `duke-build-requirement-prototype` |
| 已确认规则，需要写正式文档 | `duke-write-spec` |
| 需要验收标准或测试场景 | `duke-write-acceptance` |
| 已有 Spec/PRD，需要评审 | `duke-review-spec` |
| 同时提供需求与实现证据 | `duke-check-implementation` |
| 明确调用 `$duke-doc`、包含两个以上阶段或要求同步多个需求资产 | 进入编排流程 |

## 复杂度判断

| 维度 | L1 轻量 Spec | L2 标准需求 | L3 完整 PRD |
| --- | --- | --- | --- |
| 修改范围 | 单页面、单配置项或已有规则小改 | 多页面、模块或对象联动 | 多个核心系统或业务域 |
| 方案状态 | 已基本确定 | 主方案明确，需梳理分支 | 存在重大取舍或尚未收敛 |
| 系统能力 | 使用已有机制 | 调整已有能力或增加可控联动 | 新增关键链路、接口或基础能力 |
| 数据影响 | 无迁移或普通字段变更 | 有限存量兼容 | 大规模、复杂或不可逆迁移 |
| 风险 | 可恢复且影响有限 | 一致性、权限或依赖风险可控 | 资金、安全、合规或重大一致性风险 |

优先判断失败后果、可逆性和是否引入新机制，不按命中项机械计分。

## 变更分级

先判断本轮变化的性质，再决定是否进入跨资产编排；不要把所有原型修改都升级为完整需求传播。

| 等级 | 判断标准 | 默认执行范围 | 升级条件 |
| --- | --- | --- | --- |
| C0 视觉微调 | 间距、颜色、对齐、图标位置、换行及无业务含义的装饰变化 | 仅使用原型 Skill 修改目标区域，执行静态和浏览器检查 | 文案含义、可见条件、操作结果或业务反馈发生变化 |
| C1 展示或交互规则 | 已确认信息的展示位置、可见条件、按钮行为、反馈或场景差异变化，但不改变底层业务事实 | 更新原型、对应 `R-xxx`/`AC-xxx` 承载资产及明确直接受影响的规范性文档 | 字段语义、状态、权限、流程、接口输出或历史兼容发生变化 |
| C2 业务规则变更 | 新增、修改、替代或废弃业务规则，或改变字段、状态、权限、流程、异常、接口及历史兼容 | 使用 `duke-doc` 生成影响资产清单并执行完整传播检查 | 无 |

无法判断是 C0 还是 C1 时，检查变化是否会让研发实现出不同业务结果；会则按 C1，否则按 C0。C0 不新增业务规则编号，也不触发正式文档同步。

## 统一需求包

专业 Skill 之间使用以下字段交接，只传递当前阶段需要的内容：

| 类型 | 字段 |
| --- | --- |
| 基础信息 | 需求主题、背景、当前问题、目标 |
| 用户信息 | 目标用户、操作角色、受影响角色 |
| 范围 | 阶段树、本期范围、非本期范围 |
| 业务规则 | 规则编号、触发条件、系统处理、结果、反馈 |
| 流程 | 主流程、替代流程、失败流程、人工路径 |
| 状态 | 当前状态、允许状态、禁止状态、目标状态 |
| 权限 | 操作权限、数据权限、角色差异 |
| 异常 | 失败、部分成功、超时、重试、补偿 |
| 系统影响 | 页面、服务、接口、数据、上下游 |
| 风险 | 一致性、迁移、安全、资金、合规 |
| 数据证据 | 发现编号、来源文件、Sheet或范围、样本限制、数据发现、风险、关联问题 |
| 状态账本 | 条目编号、内容性质、确认状态、适用范围、所属阶段、来源、变更关系 |
| 资产管理 | 资产路径、资产类型、覆盖规则、同步状态、待执行动作 |
| 管理信息 | 待确认项、阻塞项、明确排除项、本轮变更摘要 |

## 编号和变更规则

- 业务规则使用 `R-001`、`R-002` 连续编号。
- 待确认问题使用 `Q-001`、`Q-002` 连续编号。
- 数据发现使用 `D-001`、`D-002` 连续编号，并保留来源和样本限制。
- 验收场景使用 `AC-001`、`AC-002`，并引用对应规则编号。
- 实现验收继续引用业务规则编号，不重新编号。
- 后续 Skill 不得静默改变已确认事实；发现冲突时记录差异并返回确认。
- 需求发生变更时保留原编号并记录新旧内容；规则被删除时标记废弃，不复用编号。
- 问题关闭后保留编号和结论；再次出现相同问题时恢复原编号，不创建语义重复的新问题。

## 组合流程

### 端到端需求交付

`访谈（按需） → 数据验证（按需） → 原型验证（按需） → 验收标准 → 文档输出 → 文档评审 → 资产一致性检查`

### 原型或数据触发回访

`已确认规则 → 原型或数据验证 → 发现冲突 → 更新待确认项 → 用户确认 → 同步受影响资产`

### 已有文档修订

`文档评审 → 用户确认业务变更 → 文档输出 → 关联资产同步`

### 实现验收

`需求口径检查（按需） → 实现验收`

### L1 快速流程

已有信息足够时跳过完整访谈，只建立简要需求包和状态账本，再按需执行原型、验收标准、轻量 Spec 和轻量读者检查。
