# 产品需求编排

## 核心职责

- 判断用户请求属于单阶段任务还是端到端任务。
- 选择专业 Skill，控制顺序、回环、交接和确认节点。
- 根据风险和用户偏好确定 L1 轻量 Spec、L2 标准需求或 L3 完整 PRD。
- 为长周期需求维护稳定编号的需求状态账本、阶段树和本轮变更摘要。
- 在确认规则变化后识别受影响资产，并检查原型、PRD、专项规则、验收标准和索引的一致性。
- 汇总最终交付结果，但不重复专业 Skill 的方法和模板。

## 编排流程

正式执行前完整读取：

- [路由与交接协议](references/routing.md)
- [需求状态账本协议](references/requirement-ledger.md)
- [资产变更传播协议](references/asset-sync.md)
- [阶段与版本协议](references/phase-version.md)
- 涉及存量数据、旧逻辑或迁移时读取 [历史兼容检查协议](references/history-compatibility.md)

### 1. 判断任务范围

- 用户只要求一个明确阶段时，使用对应专业 Skill，不继续扩展流程。
- 用户明确调用 `$duke-doc`、请求包含两个以上阶段，或要求持续维护多个需求资产时，进入编排流程。
- 已有信息足够时跳过需求访谈，不为简单需求增加不必要提问。

### 2. 建立或恢复需求状态账本

- 首次讨论时建立需求主题、阶段树、稳定编号规则和待确认问题。
- 延续项目时先读取已有需求包、原型、PRD、专项规范和本轮用户修改，恢复账本后再继续。
- 不因措辞调整重建编号；规则被替代或废弃时保留原编号和变更关系。
- 每轮结束输出本轮新增、修改、关闭和仍待确认事项；用户要求完整盘点或阶段收口时再输出完整快照。
- 将业务阶段、文档版本和发布版本分开记录，不根据“第二阶段”自动推断 `V2.0`。

### 3. 建立需求包

将用户已提供的信息整理为统一需求包。信息不足且会改变价值、范围、核心规则或验收结果时，使用 `duke-interview-requirement` 补齐。

只有访谈阶段或用户明确确认后可以新增、删除或改变业务事实。原型、数据分析、研发建议和文档评审只能提出候选方案或待确认项，不得静默升级为已确认规则。

### 4. 选择交付等级

- L1：已有机制上的小范围修改，方案明确且风险有限。
- L2：涉及多模块、状态或对象联动，存在可控系统影响。
- L3：新增关键链路，或涉及资金、安全、合规、不可逆迁移和重大一致性风险。

不要仅因出现系统联动、状态流转或接口就选择 L3。用户要求简单版时优先 L1，除非存在重大风险，并说明升级原因。

### 5. 执行并允许回环

默认主链路：

1. 按需执行 `duke-interview-requirement`，形成或更新需求包和状态账本；
2. 用户提供历史明细、导出文件或要求用数据验证规则时，执行 `duke-analyze-requirement-data`；
3. 用户需要验证页面结构或交互时，执行 `duke-build-requirement-prototype`；
4. 数据、原型或评审暴露新问题时，返回访谈阶段确认，不直接改写业务事实；
5. 执行 `duke-write-acceptance`，生成与规则编号关联的验收标准；
6. 执行 `duke-write-spec`，按交付等级和阶段版本协议组装正式文档；
7. 执行 `duke-review-spec`，检查陌生读者可理解性、历史兼容和风险；
8. 自动修复不改变业务含义的表达和格式问题；涉及规则变化时请求用户确认。

只有用户提供实现证据或明确要求实现验收时，才执行 `duke-check-implementation`。

### 6. 传播已确认变更

- 每次规则确认、替代、废弃或阶段调整后，生成影响资产清单。
- 只有资产登记或文件内容能够证明其覆盖该规则或阶段时，才标记为直接更新；仅因主题相近不得推断必须修改。
- 资产覆盖范围未知时标记“需核对”，先读取资产或请求补充，不把不确定关系写成同步结论。
- 只有用户已授权创建或更新对应文件时才执行写入；未授权资产只列为待同步。
- 更新后核对规则编号、术语、默认值、范围、阶段、链接和索引，不以“已改主文档”代替一致性检查。
- 原型演示细节、研发默认和数据建议不得传播为正式业务规则。

### 7. 控制确认节点

仅在以下情况暂停并请求用户确认：

- 需求价值、范围或核心方案存在多种方向；
- 缺失信息会导致研发实现不同结果；
- 原型或数据证据与已确认规则冲突；
- 文档评审发现 P0 问题，需要改变业务规则；
- 实现证据与需求明显冲突，但需求口径本身存在歧义。

非阻塞细节标记为待确认或实现默认，不因小问题无限延迟输出。

## 编排边界

- 不在本 Skill 中直接展开完整访谈问题库、原型实现规范、PRD 模板、测试场景或评审清单。
- 不让多个专业 Skill 分别重新判断并改写同一业务事实。
- 不为单阶段请求强制执行完整链路。
- 不把内部路由和状态管理过程写入正式产品文档，除非用户要求。

## 文档与原型写入

只有用户明确要求创建或更新文件时才写入工作区：

- 产品需求文档、专项规则和索引由 `duke-write-spec` 处理；
- HTML需求原型由 `duke-build-requirement-prototype` 处理；
- 评审报告和实现验收报告同样只在用户要求时保存。
