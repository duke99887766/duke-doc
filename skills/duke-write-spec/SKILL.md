# 产品需求文档输出

## 工作目标

将已确认的需求包和验收标准组装成深度适当、研发可执行的产品文档，并在用户授权范围内同步受影响的正式文档与索引，不重新发明业务规则。

## 输入要求

优先接收：

- 需求主题、背景、当前问题和目标；
- 阶段树、本期范围和明确排除项；
- 带 `R-xxx` 编号的已确认业务规则；
- 流程、状态、权限、异常和系统影响中的适用内容；
- 带 `AC-xxx` 编号的验收标准；
- 需求状态账本和本轮已确认变更；
- 影响资产清单及用户授权的写入范围；
- 交付等级 L1、L2 或 L3。

缺少会改变核心方案的信息时返回阻塞项，不开展完整访谈。只有非阻塞信息缺失时可以输出标记清晰的草稿。

## 工作流程

正式输出前读取 [文档输出契约](references/spec-contracts.md)。涉及多阶段、版本拆分或已上线需求的下一期延伸时，再读取 `../duke-doc/references/phase-version.md`。

1. 采用传入的交付等级；直接调用且未提供等级时，按影响范围和风险选择最轻的可用等级。
2. 只将“已确认业务规则”写成确定结论；建议、原型方案、实现默认和待确认项分别标识。
3. 按契约组织章节，省略不适用内容和空表。
4. 保留业务规则和验收标准的编号及对应关系。
5. 检查规则、流程、状态、文案、阶段和术语是否在全文一致。
6. 根据影响资产清单确定需要新建、更新或校验的正式文档和索引。
7. 覆盖范围缺少登记或内容证据时先标记“需核对”，不因主题相近直接修改。
8. 只有用户明确授权时写入对应文件；未授权资产保留为待同步项。
9. 写入后检查 Frontmatter、更新时间、关联链接、README索引和规则引用。
10. 对每个新建或更新的Markdown文档运行 `python scripts/check_requirement_docs.py <文档路径>`；仓库有索引时增加 `--index <索引路径>`，本轮要求更新时间时增加 `--expect-update-date YYYY-MM-DD`。

## 表达要求

- 默认使用中文，简洁、结论化、可执行、可验证。
- 多个字段、状态、规则、角色或场景需要比较时使用表格；简单内容不强制制表。
- 使用精确状态名、字段名、按钮名、提示语和跟进记录文案。
- 不为形式虚构指标、数据、用户证据、异常或系统影响。
- 不适用章节直接省略；只有省略可能导致误解时才写“不涉及”。

## 版本和文档沉淀

只有用户要求版本化正式文档时维护版本号和更新记录。业务阶段、文档版本和发布版本分开记录；初始正式版本使用 `V1.0`，小范围补充递增 `V1.1`、`V1.2`，重大结构或流程变化升级为 `V2.0`。已上线需求的下一期延伸优先建立新阶段或新文档，只写新改动并关联既有生效文档。

用户要求创建或更新文件时：

- 文件名使用“业务主题-文档类型.md”，避免“最终版”“最新版”；
- 若仓库存在 `docs/README.md` 和主题目录，先读取其规范、相关模板和关联文档；
- 产品需求文档使用 `文档状态` 表示文档有效性，使用 `需求阶段` 表示业务推进位置，不合并为“需求状态”；
- `负责人`填写实际维护人，不使用“产品”“研发”等角色占位；无法确认时留空并标记待补充，不自行猜测；
- 新建文档写入 Frontmatter，更新活跃文档时同步维护 Frontmatter 和 `更新时间`；Frontmatter 只保存事实字段；
- 按分类保存文档并更新索引；
- 已确认规则变化时检查关联PRD、专项规则、验收文档和索引，不静默扩大用户授权范围；
- 将不再维护的旧版本移入既有归档目录，不自行建立新的治理规则。

## 资产同步结果

完成文件更新后输出：

- 已更新资产及对应规则编号；
- 已校验但无需修改的资产；
- 因未授权、缺少文件或仍待确认而未同步的资产；
- 发现的文档口径冲突。
- 自动校验的错误、警告和未执行检查。

## 输出边界

- 不从模糊想法重新开展完整需求访谈。
- 不制作或修改HTML原型；需求原型交给 `duke-build-requirement-prototype`。
- 不独立生成详细验收场景；验收标准缺失时保留待补充提示或建议使用 `duke-write-acceptance`。
- 不对成品进行全面产品评审；需要时交给 `duke-review-spec`。
- 不读取代码或截图判断实现是否符合需求。
