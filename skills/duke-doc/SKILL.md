# 产品需求编排

## 核心职责

- 判断用户请求属于单阶段任务还是端到端任务。
- 选择需要执行的专业 Skill，并控制顺序、交接和确认节点。
- 根据风险和用户偏好确定 L1 轻量 Spec、L2 标准需求或 L3 完整 PRD。
- 保持已确认业务事实、规则编号和待确认项在各阶段间一致。
- 汇总最终交付结果，但不在本 Skill 中重复专业 Skill 的方法和模板。

## 专业 Skill

执行对应阶段前，完整读取同级安装目录中的专业 Skill：

| 阶段 | Skill | 相对路径 |
| --- | --- | --- |
| 需求访谈 | `duke-interview-requirement` | `../duke-interview-requirement/SKILL.md` |
| 验收标准 | `duke-write-acceptance` | `../duke-write-acceptance/SKILL.md` |
| 文档输出 | `duke-write-spec` | `../duke-write-spec/SKILL.md` |
| 文档评审 | `duke-review-spec` | `../duke-review-spec/SKILL.md` |
| 实现验收 | `duke-check-implementation` | `../duke-check-implementation/SKILL.md` |

若必要的专业 Skill 不存在，停止对应阶段并说明缺失项，不用编排 Skill 临时重建其完整能力。

## 编排流程

正式执行前读取 [路由与交接协议](references/routing.md)。

### 1. 判断任务范围

- 用户只要求一个明确阶段时，使用对应专业 Skill，不继续扩展流程。
- 用户明确调用 `$duke-doc`，或请求包含两个及以上阶段时，进入编排流程。
- 已有信息足够时跳过需求访谈，不为简单需求增加不必要提问。

### 2. 建立需求包

将用户已提供的信息整理为统一需求包。信息不足且会改变价值、范围、核心规则或验收结果时，使用 `duke-interview-requirement` 补齐。

只有访谈阶段或用户明确确认后可以新增、删除或改变业务事实。后续 Skill 发现缺口时返回待确认项，不得静默补造规则。

### 3. 选择交付等级

- L1：已有机制上的小范围修改，方案明确且风险有限。
- L2：涉及多模块、状态或对象联动，存在可控系统影响。
- L3：新增关键链路，或涉及资金、安全、合规、不可逆迁移和重大一致性风险。

不要仅因出现系统联动、状态流转或接口就选择 L3。用户要求简单版时优先 L1，除非存在重大风险，并说明升级原因。

### 4. 执行所需阶段

端到端需求交付默认顺序：

1. 按需执行 `duke-interview-requirement`，形成需求包；
2. 执行 `duke-write-acceptance`，生成与规则编号关联的验收标准；
3. 执行 `duke-write-spec`，按交付等级组装正式文档；
4. 执行 `duke-review-spec`，检查陌生读者可理解性和风险；
5. 自动修复不改变业务含义的表达和格式问题；涉及规则变化时请求用户确认。

只有用户提供实现证据或明确要求实现验收时，才执行 `duke-check-implementation`。

### 5. 控制确认节点

仅在以下情况暂停并请求用户确认：

- 需求价值、范围或核心方案存在多种方向；
- 缺失信息会导致研发实现不同结果；
- 文档评审发现 P0 问题，需要改变业务规则；
- 实现证据与需求明显冲突，但需求口径本身存在歧义。

非阻塞细节标记为待确认，不因小问题无限延迟输出。

## 编排边界

- 不在本 Skill 中直接展开完整访谈问题库、PRD 模板、测试场景或评审清单。
- 不让多个专业 Skill 分别重新判断并改写同一业务事实。
- 不为单阶段请求强制执行完整链路。
- 不把内部路由过程写入正式产品文档，除非用户要求说明工作过程。

## 文档写入

只有用户明确要求创建或更新文件时，才由 `duke-write-spec` 写入工作区。评审报告和实现验收报告同样只在用户要求时保存。
