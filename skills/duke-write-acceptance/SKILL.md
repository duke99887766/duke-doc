# 产品验收标准生成

## 工作目标

将已确认规则转换为研发和测试可以直接执行的验收场景，确保输入条件、操作和预期结果明确，不新增业务决策。

## 输入要求

优先使用包含规则编号的结构化需求包。至少需要：

- 操作角色或系统触发方；
- 触发条件和前置状态；
- 系统处理；
- 可观察结果；
- 禁止条件、失败处理或权限差异中的适用项。

缺少会导致不同预期结果的信息时，列为阻塞项并提出一个最关键问题。不要自行补造规则。

## 工作流程

正式输出前读取 [验收标准契约](references/acceptance-contract.md)；已有验收标准的增量修订只读取相关规则和场景，不重复加载或重写完整验收表。

1. 只提取本轮新增或变化的业务规则；保留现有 `R-xxx` 编号，缺少编号时按出现顺序补充。
2. 只为真实存在且尚无覆盖的场景生成 `AC-xxx`，不重复生成已有场景。
3. 为每个新增或变化场景定义前置条件、操作和可观察结果。
4. 检查本轮规则与既有验收的冲突、不可测试内容和口头依赖。
5. 输出增量验收表、受影响的既有场景和无法生成验收的规则缺口。

## 表达要求

- 使用精确状态名、字段名、按钮名、提示语和记录文案。
- 预期结果说明页面、业务数据、关联对象和用户反馈中的适用内容。
- 系统联动场景说明主操作、关联操作、失败后是否保留或回滚。
- 禁止场景说明入口是隐藏、禁用还是操作后报错。
- 不使用“正常处理”“合理展示”“相关状态”等不可观察表达。

## 输出边界

- 不修改或扩展需求规则；发现问题时标记需求缺口。
- 不输出完整 Spec/PRD，只提供验收标准及必要说明。
- 不根据实际实现证据给出符合或不符合结论。
- L1 只覆盖真实存在的核心场景，避免为了完整而制造大量用例。
- 完成一轮批量生成后统一检查一次；不为每个场景单独触发工作区校验。
