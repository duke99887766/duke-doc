# 产品需求访谈与规则收敛

## 工作目标

将模糊想法、零散材料或未完成方案整理为可交接给原型、文档、验收和评审 Skill 的结构化需求包，并维护可持续更新的需求状态账本，不直接输出正式 PRD。

## 访谈原则

- 先理解问题和目标，再讨论解决方案；不要把用户提出的功能直接等同于真实需求。
- 优先询问会改变价值、范围、业务规则或验收结果的问题。
- 首轮先建立范围表；同一模块且可独立回答时，默认使用带稳定编号的批量确认模式，每轮集中询问 2～4 个关键问题。只有问题高度依赖或答案会改变后续分支时才逐题询问。
- 不重复询问用户已经确认的事实。
- 将业务事实、待确认问题、原型方案、实现默认、数据发现和建议明确区分。
- 保留规则和问题的稳定编号；修改、关闭或废弃时记录关系，不删除历史或复用编号。
- 简单需求只补齐必要规则，不强制讨论基线、MVP、长期指标或完整上线方案。

## 工作流程

先判断是否真的需要访谈：已有信息能够唯一确定价值、范围、规则和验收结果时，建立简要需求包并直接交接，不重复追问。涉及历史数据、旧逻辑、迁移或合并展示时，才读取 `../duke-doc/references/history-compatibility.md`；用户提供Excel、CSV或大量明细并要求分析时，先交给 `duke-analyze-requirement-data`，本 Skill 只消费其带来源的数据发现和待确认问题。已在本轮读取且文件未变化的资料不重复读取。

### 1. 恢复已有口径

延续项目时，先从对话、已有需求包和用户提供的文档中恢复本轮目标片段：

- 需求主题和阶段树；
- 已确认业务规则；
- 仍待确认的问题；
- 暂缓、已废弃和被替代内容；
- 原型方案、实现默认和数据建议；
- 最近一次变更及受影响资产。

无法证明的内容不得因“看起来合理”被恢复为已确认规则。

同一需求已有 Codex 任务时优先延续原任务；从新任务恢复时，明确指出信息来自哪些本地文档或需求包以及仍缺失的上下文。范围未变化且目标资产未被外部修改时，不重读整份历史需求包。

### 2. 复述已知信息

简要复述背景、当前问题、目标、约束和已确认结论，指出最关键的信息缺口。日常多轮沟通只复述与本轮有关的增量，不重复完整需求包。

首次进入新需求且信息明显不足时，才整理以下范围表；用户未提供的内容保持空缺，不自行补全。已有信息足够的增量更新不重复输出整张范围表：

| 维度 | 内容 |
| --- | --- |
| 当前做法 |  |
| 当前问题 |  |
| 本期目标 |  |
| 本期范围 |  |
| 明确不改 |  |
| 复用现有能力 |  |
| 期望交付物 |  |

### 3. 判断问题与价值

按需确认：

- 目标用户或受影响角色；
- 当前发生问题的场景和现有处理方式；
- 问题频率、影响程度或业务损失；
- 期望改善的用户或业务结果；
- 为什么现在需要解决；
- 是否有数据、反馈或案例支撑。

不要为形式虚构数据或指标。价值证据不足但不阻塞小改时，说明风险后继续；可能改变需求必要性时继续澄清。

### 4. 管理范围与阶段

- 确认本期范围、明确排除项、必要的人工路径和后续优化。
- 用户将需求拆分为阶段或子阶段时建立阶段树，并记录各阶段继承、独有和排除规则。
- 后续阶段不得静默覆盖已经生效或已确认的前期规则。
- 将业务阶段与文档版本分开；阶段变化不自动推断文档大版本。
- 只有中大型需求需要进一步讨论 MVP、阶段目标和优先级。

### 5. 梳理业务规则

按需确认：

- 入口、触发条件、参与对象和前置条件；
- 展示、启用、禁用、默认值和人工覆盖；
- 主流程、替代流程、失败流程和人工路径；
- 字段、状态、权限和校验规则；
- 成功、失败、部分成功后的处理和反馈；
- 重试、补偿、撤销、记录和异常处理；
- 系统或数据影响信号。

对系统联动明确主操作、关联操作、失败处理、回滚或保留、记录和用户反馈。

存在历史数据时，对每类差异明确采用批量迁移、查询时映射、原文展示、仅兼容读取或不处理，避免只记录“兼容历史数据”。

### 6. 维护状态账本

条目使用以下状态：

| 维度 | 允许值 |
| --- | --- |
| 内容性质 | 业务规则、待确认问题、原型方案、实现默认、数据发现、建议 |
| 确认状态 | 已确认、待确认、暂缓、已废弃 |
| 变更类型 | 新增、修改、替代、被替代、废弃 |

业务规则使用 `R-001` 起始编号，待确认问题使用 `Q-001` 起始编号。用户使用旧编号回答时按原编号更新；简短回答必须补全上下文后再写入结论。

数据发现使用来源 Skill 提供的 `D-xxx` 编号，保持来源文件、Sheet或范围和样本限制；用户确认其处理方案后再形成业务规则。

### 7. 管理待确认项

- 只有缺失信息会产生不同实现结果时才标记阻塞。
- 逐题模式只适合相互依赖、答案会改变下一题或高度不确定的问题。
- 批量模式使用 `Q-001`～`Q-n`，每轮优先集中同一模块的 2～4 个问题；用户集中回答后逐项标记已关闭、仍待确认或产生新分支。
- 用户用“2”“后者”“可以”等简短表达回答时，先补全选项名称和适用范围，再写入结论，避免编号脱离上下文。
- 非阻塞细节记录为建议或实现默认，不因小问题无限延迟需求包输出。

### 8. 输出本轮变化

默认先输出本轮新增、修改、关闭和剩余待确认问题。用户要求阶段收口、完整盘点或交接时，再输出完整结构化需求包和状态账本快照。

中间交接只保留变化编号、结论、目标资产、阻塞项和最近校验；不要重复粘贴完整需求包。完整快照应在阶段收口或用户明确要求时生成一次。

## 输出契约

日常沟通使用增量模式，只输出本轮新增、修改、关闭和剩余待确认项。用户要求阶段收口、完整盘点或跨任务交接时，才读取 [完整需求包模板](references/full-requirement-package.md) 并生成一次完整快照；不同时输出重复的增量表和完整账本。

## 边界

- 不选择正式文档模板或编写完整 PRD。
- 不制作或修改HTML原型，只向原型 Skill 交接已确认规则和原型假设。
- 不生成成套验收场景，只记录每条规则应产生的可观察结果。
- 不评审自己输出的文档质量。
- 不依据截图、代码或测试报告判断需求是否已经实现。
